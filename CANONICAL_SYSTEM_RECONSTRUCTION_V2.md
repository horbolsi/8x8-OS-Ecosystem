## 1. Definition

8x8 is a supervised, owner-governed, distributed AI operator fabric. It coordinates identities, agents, missions, memory, messages, models, connectors, local runtimes, public applications, creative production, research, market intelligence, and restricted blockchain laboratories through bounded authority, provenance, receipts, rollback, and explicit activation gates.

8x8 is not one application, one repository, one AI agent, one dashboard, or a replacement hardware kernel.

## 4. Authority model

FlashTM8 Owner is the sole highest-impact authority. No agent, connector, caller-provided claim, planning record or mirror may silently inherit owner authority.

Exact fresh approval is required for consequential operations including production deployment, service mutation, credential use, database mutation, public posting, email sends, trading, wallet operations, blockchain transactions, destructive cleanup and unrestricted external execution.

## 5. Agent and presence model

The recovered canonical council includes FlashTM8 Owner, FlashTM8 Proxy, Hermes, Claude, ChatGPT, OpenClaw, Aegis, Trader, Architect, Scribe, Curator and Council Moderator.

Agent names in files do not prove live presence. ACTIVE or BUSY requires a canonical identity, authenticated fresh heartbeat, nonce, task receipt and provider/model attestation. Silence is not a vote. Offline or unauthenticated agents are excluded from quorum.

## 6. Mission lifecycle

Owner intent -> mission envelope -> authority resolution -> bounded context retrieval -> agent/model routing -> proposal -> required approval -> scoped execution -> validation -> receipt -> state projection -> memory curation -> public-safe mirror synchronization -> cockpit result -> continuation or handoff.

Every mature mission should bind task IDs, identities, source digests, constraints, tests, receipts, artifacts, rollback and completion state.

## 7. Hermes role

Hermes is the coordination and routing layer. Recovered tools cover provider registries, provider health, deterministic model route planning, capability graphs, task queues, mission bootstrap, memory diffs, GitHub PR watching, research planning and autonomy handoffs.

Planning or route generation is not execution. Provider fallback is bounded by privacy, health, task suitability, retry limits and circuit breakers.

## 8. Memory and messages

The memory system separates append-only events, deterministic state projections, semantic memory, session indexes, redacted logs, knowledge graphs, artifact graphs, task-aware retrieval, contradiction handling and rollback.

The messages repository separately stores attributable communication evidence. The runtime ledger, message evidence and curated memory are distinct authorities and must not be collapsed into one undifferentiated store.

## 9. Runtime mesh

Documented nodes include Samsung Android, Termux, Ubuntu PRoot, Android shared storage, an iPhone/iSH auxiliary node, GitHub clean worktrees, Replit and cloud adapters. The live runtime and public synchronization lanes must remain separate. Dirty operational trees must never be bulk-staged into public repositories.

Current live local state is not verified from this chat. Historical receipts remain historical until a fresh signed census is produced.

## 10. Unified Cockpit

The intended Cockpit consumes one canonical API and event fabric. It covers Mission Control, Agent Fleet, Workflows, Studio, Memory, Model Fabric, Connectors, Security, Infrastructure, Trading Intelligence, Publishing, Cloud Status, Owner Decisions and Incident Recovery.

2D is the primary reliable interface. 3D/360 is an optional visualization of the same canonical objects. Decorative activity must never imply unproven live capability.

## 11. Studio

Studio is an artifact lifecycle system, not only generation. Every file, URL, image, video, audio or text input may become a provenance-bound artifact with privacy/copyright classification, research, scripts, storyboards, assets, edit history, quality checks, owner approval, publishing gates and analytics references.

Creation and public publishing remain separate authorities.

## 12. Markets and blockchain

Trading remains signal-only and read-only unless a separate exact risk gate authorizes execution.

The blockchain repository is a testnet laboratory for a reconciled multi-asset model across selected test networks. Mainnet promotion, private-key handling, arbitrary signing, unlimited trading and unsolicited marketing remain blocked.

## 13. Connector hierarchy

Fresh runtime receipts outrank GitHub; GitHub code and reviewed releases outrank mirrors; message evidence and curated memory preserve context; Drive and Notion are controlled mirrors; Airtable is structured registry; ClickUp is planning; design and communication systems do not become implementation truth.

Connector lifecycle:

DISCOVERED -> CONFIGURED -> AUTHENTICATED -> READ_VERIFIED -> WRITE_VERIFIED_BOUNDED -> RELEASE_LINKED -> PRODUCTION_APPROVED

## 14. Continuous autonomy

8x8 targets continuous bounded autonomy: observe, classify, plan, test, document, patch clean branches, scan, report, synchronize public-safe artifacts and escalate consequential actions.

It does not authorize unlimited self-directed trading, wallet activity, public posting, destructive mutation, paid-provider use or production deployment.

## 16. Present conclusion

8x8 is best understood as a governed operating fabric for verifiable AI work across private owner infrastructure and public-safe products. Its differentiator is not unlimited autonomy. It is the combination of coordinated agents, bounded authority, durable context, attributable evidence, multi-node execution, creative and analytical domains, and explicit human control.
