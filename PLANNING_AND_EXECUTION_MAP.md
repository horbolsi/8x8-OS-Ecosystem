# 8x8 Planning and Execution Map

This document defines how planning systems relate to canonical implementation truth.

## Authority order

1. Fresh runtime receipts and deployed SHA
2. Reviewed GitHub code, releases, CI, issues, and pull requests
3. Private message evidence and curated memory
4. Google Drive continuity and recovery artifacts
5. Notion human-readable maps and decision indexes
6. Airtable connector, workstream, and activation-gate metadata
7. ClickUp long-horizon planning and task decomposition
8. Other connected project systems only after evidence-backed adoption

Planning completion never proves implementation, deployment, security, financial activation, or runtime health.

## ClickUp

- blockchain and on-chain architecture

- mobile and web dashboard UX
- sub-agent systems frameworks
- seeded sub-agent task structures

ClickUp is classified as a **planning mirror**. Every ClickUp item must resolve to one of:

- a linked GitHub issue or pull request
- a canonical specification
- an archived historical plan
- a rejected or contradicted item
- an UNKNOWN item awaiting evidence

## Reconciliation requirements

For every planning item:

- preserve source URL and original title
- record source system and last-modified timestamp
- classify maturity and truth state
- identify canonical GitHub target
- identify owner and next evidence gate
- identify security, financial, public-write, and deployment risk
- record keep, rebuild, merge, archive, reject, or unknown decision

## Duplicate and drift controls

The current connected estate already shows duplicate Airtable connector rows and repeated ClickUp document search surfaces. Therefore:

- connector name must be unique within the canonical registry
- duplicate records must be merged only after field-level reconciliation
- repeated search surfaces must be traced to their real parent document
- no status may be upgraded based only on duplicate agreement
- freshness must be recorded separately from completeness

## Required lifecycle

`DISCOVERED -> CLASSIFIED -> CANONICALLY_LINKED -> IMPLEMENTED -> TESTED -> RECEIPTED -> DEPLOYED -> FRESHLY_VERIFIED`

Any item may also terminate as `ARCHIVED`, `REJECTED`, `CONTRADICTED`, or `UNKNOWN`.
